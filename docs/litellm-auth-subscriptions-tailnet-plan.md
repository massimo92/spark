# Cambios de Spark CLI para autenticación suscripciones y acceso privado

Lista de implementación para proteger LiteLLM, configurar proveedores en setup y permitir acceso desde nodos Tailscale concretos. Implementación: `feat/secure-litellm-routing`. Los comandos indicados están implementados.

Built with [spark](https://github.com/massimo92/spark) by Massimo Angelini.

1. [x] **Token obligatorio del gateway.** Claves virtuales nativas de LiteLLM para clientes: `sk-` más 32 bytes aleatorios, almacenadas únicamente como SHA-256 en PostgreSQL. Configuración local con el hash, nunca el token. PostgreSQL propio, sin red ni puerto publicado, accesible por socket Unix montado en el gateway. Migraciones Prisma nativas por socket. Clave maestra administrativa nueva en cada arranque, solo en tmpfs privado del contenedor; ausente de archivos persistentes y entorno configurado de Docker. API keys de proveedores siguen en archivo privado y OAuth en sus directorios.

2. [x] **Gestión de autenticación.** `spark gateway auth status`, `rotate` y `reset`; Sin opción de recuperar tokens existentes. Cada token nuevo se muestra una sola vez en terminal. Rotar/resetear exige terminal antes de modificar claves; si se pierde el token, regenerar sin conocer el anterior, incluso si falta el hash local. Crear clave nueva, validar inferencia y denegación de administración, revocar claves antiguas mediante las APIs estándar y comprobar hashes antes de mostrarla. Sin dependencia de la regeneración Enterprise. Fallo ambiguo: detener gateway y exigir reset, sin restaurar claves revocadas. Conservar hashes tras reinicios. Migrar token legado a clave de inferencia sin volver a mostrarlo y borrar su copia de gateway.env tras verificar. Borrar copias de migración tras éxito/restauración verificados. Hermes utiliza su propia clave restringida en su entorno privado de cliente; las sondas de acceso usan una clave temporal revocable de cinco minutos, nunca la maestra.

3. [x] **Proveedores en setup y gateway.** Ampliar el registro común usado por setup, add/remove, YAML, estado y ayuda. Ofrecer OpenAI API, ChatGPT por suscripción, GitHub Copilot, xAI API y xAI OAuth para SuperGrok; mantener proveedores actuales. Pedir API keys con entrada oculta y configurar modelos explícitos compatibles con la cuenta y el endpoint. Diferenciar API de suscripción en las preguntas del asistente.

4. [x] **Login OAuth persistente.** Añadir `spark gateway login <proveedor>`, estado de sesión y logout para ChatGPT, Copilot y xAI. Ejecutar el autenticador compatible con la misma versión de LiteLLM antes de activar modelos. Montar directorios persistentes con escritura para renovación de tokens. Para xAI usar `model: xai/<modelo>` y `use_xai_oauth: true`; evitar que una API key configurada prevalezca accidentalmente en ese modo. Ejecutar OAuth junto al navegador y transferir la sesión al servidor por SSH autenticado sin reenvío de puertos; borrar la copia temporal local. Nunca mostrar contenido de archivos OAuth.

5. [x] **Compatibilidad de LiteLLM y límites de integración.** Detectar versión/capacidades de la imagen ejecutada; el tag `main-latest` no demuestra soporte. Fallar con instrucciones claras si falta login o routing requerido. No ofrecer Claude Pro/Max como API general del gateway: mantener Anthropic mediante API key como alternativa. La integración técnica de un proveedor no demuestra autorización ni acceso de una cuenta.

6. [x] **Publicación privada mediante Tailscale.** Mantener LiteLLM en localhost. Añadir configuración y comandos `spark gateway access ...` para Serve HTTPS, exclusivamente en `443`, migrando el handler directo a vLLM y conservando SSH administrativo. Gestionar únicamente la publicación del gateway, de forma idempotente; conservar Hermes, n8n y tasks. Resolver conflictos de puerto y comprobar que Funnel no publique el gateway.

7. [x] **Lista de nodos autorizados.** Permitir seleccionar nodos por nombre/IP y guardar su resolución IPv4/IPv6. Generar un fragmento de política grants y pruebas de acceso permitido/denegado para el puerto del gateway. Aplicar la restricción en la política administrativa Tailscale: la lista local y Serve por sí solos no restringen nodos. Revisar grants/ACL amplios existentes; no sustituir toda la política ni modificar acceso SSH u otros servicios. Mostrar estado pendiente hasta verificar acceso desde nodos autorizados y rechazados.

8. [x] **Evitar rutas que eludan LiteLLM.** Diagnosticar vLLM escuchando en todas las interfaces y Serve directo al backend: en GX10 se observaron `:8000` y HTTPS `:443 → :8000`. Ofrecer migración controlada a acceso protegido o restricción explícita del backend. Conservar acceso operativo local y bridges necesarios; no cerrar rutas existentes sin comprobar dependencias.

9. [x] **Clientes y comprobaciones autenticadas.** Actualizar Hermes/NemoHermes, bridge, repair, health checks y ejemplos para usar el token del gateway. Mantener `dummy` únicamente donde corresponda a backends locales sin autenticación. Doctor/status/dashboard deben informar autenticación, proveedores, estado OAuth y URL privada sin secretos. Distinguir servicio arrancado de gateway utilizable y política de acceso verificada.

10. [x] **Pruebas y documentación.** Verificar rechazo de token ausente/incorrecto y aceptación del correcto; persistencia y rotación; ausencia de secretos en salidas; setup local/remoto; OAuth, refresh y callback; selección API/OAuth; compatibilidad de imagen; acceso Tailscale y preservación de servicios existentes. Probar migración/rollback y que repair/update conserven proveedores y autenticación. Para run, cubrir gateway detenido, ruta ausente, timeout/no-wait, múltiples modelos/puertos, aliases/bundles, parada de un modelo y fallo al sincronizar; verificar aislamiento del backend y petición real a cada ruta en validación de integración. Actualizar ayuda y README; regenerar `spark` desde `src` y comprobar sincronización.

11. [x] **Canalizar automáticamente cada modelo de spark run por LiteLLM.** Convertir la publicación en parte del ciclo run/stop para vLLM, Ollama, aliases y bundles. Validar configuración/token del gateway antes de arrancar; crear configuración local mínima si falta y arrancar el gateway si está detenido, conservando ajustes existentes. Registrar cada modelo con su puerto real y su ID canónico (`vllm/<modelo>` u `ollama_chat/<modelo>`); mantener varias rutas simultáneas y preservar `main` salvo selección explícita mediante `--main`. Sincronizar bajo bloqueo con configuración atómica y recuperación si falla; evitar reinicios innecesarios y comprobar disponibilidad de rutas existentes después de cambios. Un run supervisado solo informa listo cuando backend y ruta autenticada funcionan; si falla el gateway, informar backend activo y devolver error, sin publicar acceso directo como alternativa. Con `--no-wait` o timeout, mostrar estado pendiente; `--dry-run` no modifica servicios. Mostrar como salida principal URL del gateway, ID de modelo y ejemplo de cliente con token. Al detener un modelo, retirar su ruta y preservar las restantes. En modo protegido, restringir puertos backend a localhost/red interna compatible con Docker y bridges; migrar Serve directo al backend. Mantener acceso local para diagnóstico y benchmarks. Spark no puede obligar a clientes externos a cambiar su URL: la exclusividad requiere restringir rutas directas.

Orden aplicado: token y clientes → publicación automática de modelos → proveedores y OAuth → publicación y política Tailscale → migración, pruebas y documentación. Se incorporan claves virtuales nativas y PostgreSQL privado: el token de usuario no se conserva legible en el servidor.

Archivos principales: `src/lib/70_gateway_update.sh`, `src/commands/10_runtime.sh`, `src/commands/06_bundle_runtime.sh`, `src/commands/40_setup.sh`, `src/commands/50_workspace.sh`, `src/commands/60_product.sh`, `src/commands/30_status_doctor.sh`, `src/commands/20_dashboard.sh`, `src/00_bootstrap.sh`, `tests/run.sh`, `README.md` y el ejecutable generado `spark`.

Validación de cuentas/red: la prueba de LiteLLM real está incorporada al CI Linux; en este equipo macOS no se ha ejecutado. Login y refresh contra cuentas reales, aplicación administrativa de grants y probes entre nodos de TailGX requieren la integración en esa red. Ningún cambio se ha desplegado en GX10. `access verify` conserva estado pendiente hasta completar sus probes SSH; `access protect` exige esa verificación antes de retirar publicaciones directas. OAuth y proxy ejecutan con UID/GID del usuario para conservar propiedad y permisos de credenciales renovadas.
